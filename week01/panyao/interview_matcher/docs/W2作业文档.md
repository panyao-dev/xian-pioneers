# W2 作业：Zero-Shot / Few-Shot / CoT 提示策略对比

## 1. 本周目标

在 W1 已调通 GLM 网关与工具调用的基础上，用真实 Android 简历对比三种提示策略对"简历标签抽取"的效果差异：

- **Zero-Shot**：只给任务说明、词表和输出格式，不给示例；
- **Few-Shot**：在 Zero-Shot 基础上加 1 份独立车机方向示例（简历 → 标准 JSON）；
- **CoT**：要求模型先按"列事实 → 分深度/配套/不适合 → 映射词表"三步推理，再输出 JSON。

三套 Prompt 共用同一套词表、字段定义和输出契约，唯一变量是"给不给示例"和"要不要分步思考"，保证差异可以归因到策略本身。

## 3. 本轮汇总（4 份 × 3 策略，共 12 次真实调用 glm-5.2）

### 3.1 策略级统计

| 策略 | 解析成功 | 字段完整 | OOV 记录 | OOV 标签 | 平均 total token | 平均 completion | 层级/core/配套/不适合 均条 |
|---|---|---|---|---|---|---|---|
| Zero-Shot | 12/12 中的 4/4 | 4/4 | 1 | 网络框架 | 5502 | 2688 | 2.0 / 6.0 / 5.0 / 7.2 |
| Few-Shot | 4/4 | 4/4 | 1 | 网络框架 | 6158 | 3244 | 2.0 / 6.0 / 5.0 / 6.8 |
| CoT | 4/4 | 4/4 | 2 | 网络框架 ×2 | **6876** | **3985** | 2.0 / 6.0 / 5.0 / 7.2 |

> 全部 OOV 都是模型简写 `网络框架`，词表全称是 `网络框架(OkHttp/Retrofit)`；属于标签写法简写，不是简历内容落在 Android 词表外。除该简写外，其余标签均命中封闭词表。

### 3.2 逐份三策略观察

| 简历 | Zero-Shot 主要输出 | Few-Shot 主要输出 | CoT 主要输出 |
|---|---|---|---|
| 王嘉 | 层级 系统应用+App 层；core：SystemUI、Settings、相机、联系人、行业终端、分屏 | 层级误补 `车机专项`；core 多 `锁屏/Keyguard`；其余接近 zero | 层级 系统应用+App 层；core 与 zero 基本一致 |
| 陈明英 | core：SystemUI、锁屏、AOD、插件化、Compose、ANR/卡顿 | core：SystemUI、锁屏、AOD、冷启动、插件化、Compose；secondary 补串口/时钟 | core：SystemUI、锁屏、AOD、插件化、冷启动、ANR；Compose 降到 secondary |
| 李丽霞 | core：SystemUI、锁屏、通知栏、Jetpack、BLE、自动化测试 | core：SystemUI、锁屏、通知栏、AMS/WMS、BLE、分屏；Compose/Flutter 进 secondary | core：SystemUI、锁屏、通知栏、AMS/WMS、BLE、ANR；Jetpack/自动化进 secondary |
| 谢志文 | core：Launcher3、WebView/浏览器、下载管理、ANR、冷启动、包体积 | core 与 zero 一致；网络框架简写 OOV；功耗优化进 secondary | core 与 zero 一致；网络框架简写 OOV；四大组件进 not_suitable |

### 3.3 一致与分歧

**三策略较一致的判断**：
- 陈明英 SystemUI / 锁屏 / AOD；李丽霞 SystemUI / 锁屏 / 通知栏 / BLE；谢志文 Launcher3 / 浏览器 / 下载管理 / 性能优化，这几组 core 在三策略间基本稳定。
- 底层相邻方向（Binder、AMS/WMS、HAL、Linux 内核、HIDL/AIDL、SELinux）普遍进 `not_suitable`，方向一致。

**策略间摇摆或偏差**：
- **深度/配套位置浮动**：Settings、四大组件、Jetpack、Compose、自动化测试、Flutter 在 core / secondary 之间上下移动，单次运行受模型随机性影响明显。
- **层级多选倾向**：四份平均层级 2.0，普遍多补一个 App 层或 Framework 层；王嘉 Few-Shot 还把行业终端误归到 `车机专项`（记录仪/车台 ≠ 车机座舱专项）。
- **not_suitable 混入已涉及方向**：陈明英 CoT 把 `功耗优化 / 内存泄漏治理 / 包体积瘦身` 列入不适合；李丽霞 CoT 把 `AOD / Perfetto / 冷启动 / Launcher3` 列入不适合；谢志文三策略都把 `SystemUI定制` 列入不适合。这类"相邻但有实践"的边界，推理链并没有收紧，反而更容易展开过度。

## 4. 总结

**4.1 结构化稳定性来自封闭词表 + 输出契约，不是提示策略。** 12 次调用解析成功率、字段完整率都是 100%；真正兜底的是：标签只能从词表选、字段固定、JSON 契约明确。这部分是硬约束，不随策略变化。

**4.2 成本排序：Zero < Few-Shot < CoT，CoT 成本最高且收益不稳定。** 平均 completion 2688 / 3244 / 3985，平均 total 5502 / 6158 / 6876。CoT 的 reasoning 单独占输出，长简历（陈明英 5622、李丽霞 4596 completion）成本放大明显；但本轮观察里 CoT 没有换来更准的边界，反而在 not_suitable 引入新的误判。

**4.3 Few-Shot 标签写法最贴词表，价值在"给边界样例"。** 4 份里只有谢志文 1 次出现 `网络框架` 简写；示例主要对齐了"配套怎么放、标签怎么写全称"。Few-Shot 不是降低成本（prompt 多带一段示例），而是把软判断边界向词表口径拉齐。

**4.4 Zero-Shot 最省，但规则遵循最弱。** 无示例可参照时更容易简写标签、漏放基础项；适合作为基线，不适合作为默认生产策略。

**4.5 三类共性错误，提示策略救不了，要靠词表 / 规则层兜底：**
1. **层级多选**：边界不清时模型倾向多补一个层级；`行业终端` 与 `车机专项` 这种相邻归类需要规则或词表说明约束。
2. **深度 / 配套边界模糊**：完整落地 vs 会用过的判定，单次运行不稳定，需要更多贴近业务的边界示例或人工 gold 校准。
3. **not_suitable 被填满甚至混入已涉及方向**：相邻方向都被挑进来，个别把做过的性能/系统应用方向也打入不适合；需要规则层限制条数、禁止把 core 相邻标签重复塞进 not_suitable。

## 5. 黄金万能提示词公式

从本轮对比反推，可复用的结构化抽取 Prompt 按以下七段拼装：

```
【1. 角色与边界】你是谁；只做什么；明确不抽取什么（个人信息、未提及内容）。
【2. 封闭词表】层级词表 + 技能词表；禁止造词，词表外说法映射到最接近的已有标签。
【3. 分层定义 + 数量上限】core / secondary / not_suitable 各自判定标准与条数区间；
   区分"深度主导、完整落地"与"会用过、非主攻"；相邻但无深度实践才进 not_suitable。
【4. 结构化输出契约】固定字段名、JSON 对象、不要解释和代码块；缺项用空列表。
【5. 1~2 份贴近业务的边界示例】优先演示易错边界：配套怎么放、什么留空、不适合怎么挑、标签写全称。
【6. 可选分步检查清单】仅难样本使用：先列事实 → 再归类 → 最后映射词表；
   推理过程单独放 reasoning 字段，不污染结果字段。
【7. 工程兜底（在 Prompt 之外）】词表校验、条数校验、规则层硬过滤；
   不把"层级一致 / 是否在职 / 轮次角色"这类判断全交给模型。
```

要点：**硬约束（词表、字段、条数）写进 schema / 代码兜底；软判断（深度边界）用示例对齐；推理链只在需要审计时开启。**

## 6. 真实简历接入验证

- 入口：`uv run w2-real <pdf...>`（不传策略默认三策略全跑；可最后传 `zero_shot / few_shot / cot`）。
- 脱敏：pypdf 抽文本，行级正则剥掉电话 / 邮箱 / 链接 / 日期 / 院校 / 姓名；四份脱敏文本均无电话、邮箱、院校残留。
- 非目标方向参考：`Downloads\简历.pdf`（Java 后端校招，Spring/MySQL/Redis/Dubbo/FastDFS）不在 Android 词表内；Zero-Shot 正确留空，Few-Shot 曾误补层级与 not_suitable。后续流程应加"非目标方向"显式分支：四字段留空 + `out_of_scope` 标记，不硬凑层级。
