与 W3 的分工值得先说清楚，因为两者都涉及"校验"：

- **W3 的反思是后置的**——工具跑完，判断"这个结果可信吗、合规吗"，问题在结果层；
- **W4 的校验是前置的**——工具还没跑，判断"这个调用允许吗、参数合法吗"，问题在入参层。

两者不是替代关系，而是纵深：W3 挡住"结果不合规"，W4 挡住"调用根本不合法"。W3 的反思救不了 `interviewer_id=123` 这种参数错，W4 的 schema 校验也不会察觉"工具返回了空时段却编了个时间"。这两类失败必须分别拦。

# 三、设计出发点：为什么手写，而不是用框架

框架能替你做的：消息编排、工具注册、状态持久化、checkpoint、可视化。框架不会替你做的：**判定"这一步到底该不该执行"**。而这恰好是本期作业的核心。

三个具体理由：

1. **控制权**。Loop 的本质是一串"是否继续"的判断：模型要不要继续调工具、参数能不能执行、回答能不能交付、轮数还剩多少。把这些判断交给框架的默认策略，出问题时你只能改配置；手写则每一处都能插闸门、能打日志、能改判据。
2. **可测试性**。手写后，`validate_input` / `validate_tool_args` / `validate_output` 都是纯函数，单测不需要模型、不需要网络。本期参数与输出闸门的验证全部在单元层完成，零 token 消耗。
3. **故障可归因**。框架的失败往往是一段笼统堆栈；手写的循环给出的是 `terminated_by=invalid_args` 这种可枚举原因，能直接进监控打点。

代价也明确：没有 checkpoint、没有断点续跑、没有多 Agent 编排。这些是 W5 之后要加的东西，而不是本周该承担的复杂度。

# 四、Loop 的结构与不变量

## 4.1 主循环

```
输入 question
   │
   ├─ 闸门① 输入校验 ── 不通过 ─→ terminated_by=input_invalid（不进循环）
   │        │通过
   ▼
 ┌──────────────────────────────────────────────┐
 │ for step in 1..max_steps                     │
 │   ├─ 调模型（带 tools schema）               │
 │   ├─ 有 tool_calls？                         │
 │   │    ├─ 是 → 闸门② 工具名合法性            │
 │   │    │        └─ 未注册 → 回灌 error，跳过执行
 │   │    ├─ 闸门③ 参数校验                     │
 │   │    │        └─ 不通过 → 回灌 errors+hint，不执行
 │   │    ├─ 执行（异常包成 error，不击穿 Loop）
 │   │    └─ 结果以 role=tool 回灌 → 下一轮     │
 │   └─ 否 → 收敛候选                           │
 │        └─ 闸门④ 输出校验                     │
 │             ├─ 通过 → answered               │
 │             └─ 不通过 → 回灌修正，限 1 次    │
 └──────────────────────────────────────────────┘
   │
   └─ 轮数用尽 → max_steps（ok=False + 原因）
```

## 4.2 四条不变量

手写 Loop 最容易犯的错是"看起来在循环，实际上状态在漂"。所以我把约束写成不变量，代码里逐条对应：

| 不变量 | 含义 | 违反会怎样 |
|---|---|---|
| **单步单次决策** | 每轮只调一次模型，一轮内的多个 `tool_calls` 全部处理完才进下一轮 | 半途进入下一轮，模型会重复调同一工具 |
| **工具调用必有应答** | 每个 `tool_call_id` 都必须有一条 `role=tool` 消息，无论成功还是被拒 | 缺少应答会被网关判为消息序列非法（400） |
| **校验失败必有原因** | 拒绝时回灌 `errors` + `hint`，不只回一个 `false` | 模型无法自我修正，下一轮大概率犯同样的错 |
| **累积用量恒增** | 每轮 `step` 递增，且循环出口只有四个 | 无出口的循环只能靠 kill 进程，线上不可接受 |

第三条是本期真正有价值的一条：**校验的价值不止在"拦"，更在"拦完之后还能继续"**。

## 4.3 为什么校验要"回灌"而不是"抛错"

工具参数由模型生成，天然会错。抛异常意味着这次请求白跑，用户还得重来；回灌意味着模型看到"哪个字段、错在哪、期望是什么"，下一轮多数能改对。所以两道参数闸门都把结构化错误写进 `role=tool` 消息：

```json
{"error": "参数校验未通过，工具未执行",
 "errors": ["...channel 取值 'mail' 不在允许范围 ['group', 'private'] 内"],
 "hint": "请按 schema 修正参数后重试"}
```

这里有个容易忽略的细节：错误必须挂在对应的 `tool_call_id` 上，而不是另起一条 system 消息。否则模型分不清"是哪个调用失败了"，多工具并行时会张冠李戴。

## 4.4 终止原因可枚举

`terminated_by` 固定四值：`answered` / `max_steps` / `input_invalid` / `output_invalid`。这不是日志装饰，而是可观测性的起点：

- 调用方不用解析自然语言，直接判成败；
- 线上按原因分布看问题：`max_steps` 高说明任务拆得太深或工具不够用；`input_invalid` 高说明上游传参有问题；`output` 类异常高说明 prompt 约束不到位。

退出码同步区分：`answered` 为 0，其余为 1，方便 CI 与脚本化调用。

# 五、校验层设计

## 5.1 分层原则

四层校验按"离副作用有多远"排布，越靠近边界越早拦：

```
输入 ──→ 工具名 ──→ 参数 ──→ 执行 ──→ 输出
 ↑最外层           ↑无副作用可查     ↑有副作用，尽量晚     ↑已产生副作用，只能事后补救
```

原则有三条：

1. **能在无副作用处拦，绝不在有副作用处判**。参数错在调工具前就该拒，不能等工具跑完再看结果对不对——那时代价已经付了。
2. **fail-closed 优先**。拿不准就拒绝并回灌原因，而不是放过去赌模型自觉。
3. **校验器与业务解耦**。`validation.py` 不 import 任何工具实现，只认 schema；换工具只换 schema，不改校验逻辑。

## 5.2 输入校验（闸门①）

| 规则 | 阈值 | 后果 | 为什么是这个口径 |
|---|---|---|---|
| 必须是字符串 | `isinstance(str)` | 拒绝 | None / dict 传进来后面必然崩，早拦省得追栈 |
| 最小长度 | 4 字符 | 拒绝 | 挡误触发的空请求与单字噪声 |
| 最大长度 | 2000 字符 | 拒绝 | 防超长文本挤爆上下文，也让 token 成本可预期 |
| 空字节 | `\x00` | 拒绝 | 常见于拼接污染或复制异常，属于非法内容 |

长度上限取 2000 是工程折中：本业务单次请求（候选人 + 需求描述）远低于此，超过基本是上游拼错。

## 5.3 工具参数校验（闸门②③）

用 JSON Schema 的一个**严格子集**自己实现，不引 `jsonschema` / pydantic。理由是：本期工具 schema 结构简单，引入依赖增加的维护面大于收益；自己实现反而能把每条规则的行为写死、写清楚。

| 规则 | 实现要点 | 示例错误 |
|---|---|---|
| 工具名已注册 | schema 查不到即拒绝，不尝试模糊匹配 | `未知工具：foo` |
| arguments 是合法 JSON 对象 | 先 `json.loads`，失败不执行 | `arguments 不是合法 JSON` |
| 类型匹配 | `string/array/object/integer/number/boolean` | `candidate_ref 类型错误：期望 string，实际 int` |
| `bool` 不冒充 `integer` | Python 里 `True` 是 `int` 子类，需显式排除 | `期望 integer，实际 boolean` |
| 必填字段 | 逐项检查 `required` | `缺少必填字段：recommend` |
| 枚举约束 | `channel ∈ {group, private}` | `取值 'mail' 不在允许范围` |
| 未定义字段 | 默认严格，schema 外字段一律拒 | `出现未定义字段：channel` |
| 数组元素递归 | `items` 内再走一遍类型/必填 | `recommend[0] 缺少必填字段：interviewer_id` |
| 元素数量 | `minItems / maxItems` | `元素过多：最多 3 个` |
| 执行异常兜底 | `TypeError` 与其它异常都包成 error | `工具执行异常：KeyError: ...` |

几个值得写下来的取舍：

- **`bool` 陷阱**：`isinstance(True, int)` 为真。若不显式排除，模型传 `{"top": true}` 会通过 `integer` 校验，然后在下游做算术时炸掉。这类"静默通过"比直接报错危险得多。
- **严格拒绝未定义字段**：好处是能立刻暴露"模型自创字段"（比如给日历工具硬塞 `channel`），坏处是模型若传 `additionalProperties` 之外的合理扩展也会被拒。当前选择严格，因为工具 schema 是封闭业务接口，多余字段本身就是理解偏差的信号。
- **未实现 `oneOf / anyOf / $ref`**：本期 schema 用不到，硬加会让实现复杂度失控。这是有意识的减法。

## 5.4 输出校验（闸门④）

输出校验是本期最难的一块，因为**语义越界不可用规则完备表达**。所以这里不是"全覆盖"，而是挑几个高价值、可判定的点：

| 规则 | 口径 | 为什么加 | 局限 |
|---|---|---|---|
| 非空且 ≥8 字符 | 长度阈值 | 防空回答被当成功 | 长而无意义仍会通过 |
| PII 泄漏 | 手机号 / 邮箱 / 身份证正则 | 简历侧已脱敏，出口不能再漏 | 变形号码（分隔符）测不出 |
| 编造工号 | 所有 `XA-\d{4}` 必须在池中 | 防模型顺手编一个不存在的面试官 | 只覆盖本业务命名格式 |
| 业务越界表述 | 「已自动派单 / 已通知面试官 / 已锁定会议 / 已创建会议 / 已回写招聘系统」 | 项目红线：只推荐，不派单、不锁会、不回写 | 只认字面，改写说法（"已经安排下去了"）拦不住 |
| 必须提示确认 | 出现「确认」 | 推荐清单必须停在待 HR 确认 | 仅 warning，不阻断 |

关键判断：**越界表述用 error，提示确认用 warning**。原因是对精确率与召回率的权衡——把"没说确认"判成失败，误杀率会很高（模型用"待确认""请您定稿"等表述都算合规），而把"已自动派单"判成失败几乎不会误杀。所以前者只降级为提醒，后者直接阻断并回灌修正。

这条也暴露了当前方案的真实短板：**字面匹配挡不住语义等价的越界**。要根治得靠结构化输出（让模型只在受控字段里表达结论）+ 下游渲染，而不是靠正则兜文本。

## 5.5 轮数限制（闸门⑤）

- 默认 `MAX_STEPS=5`；本期最长链路是 3 次工具调用 + 1 次作答，5 留了 1 轮余量给参数纠错；
- 轮数用尽是**正常出口**：返回 `ok=False`、`terminated_by=max_steps`、带 `errors`，不抛异常也不返回半截答案；
- 为什么不是无限循环 + 超时：超时是"时间到了才停"，轮数是"预算到了就停"。前者不可预测（一次慢调用就可能吃掉整个超时），后者成本上界可算。

尚未做但应当做的两件事，我明确记在这里而不是假装已实现：

1. **重复调用检测**——模型可能反复调同一个工具、同一参数。当前没有 fingerprint 去重，只靠轮数兜底；
2. **工具级超时**——工具目前是本地只读实现，耗时可控；接真实外部 API 后必须加 `timeout`，否则单次调用能吃掉整个预算。

# 六、失败模式矩阵

把 Agent Loop 常见故障与本期对应闸门放在一张表里，能看清哪些已覆盖、哪些仍有残留风险：

| 失败模式 | 典型症状 | 对应闸门 | 当前处理 | 残留风险 |
|---|---|---|---|---|
| 输入垃圾 | 空串、超长、非字符串 | ① 输入校验 | 直接拒绝，不进循环 | 语义无关但格式合法的输入测不出 |
| 调不存在的工具 | `tools` 里没有该 name | ② 工具名 | 回灌 `未知工具`，跳过执行 | 模型可能换个名字继续试，靠轮数兜底 |
| 参数幻觉 | 字段名错、枚举越界、类型错 | ③ 参数校验 | 回灌结构化错误 + hint | 模型可能连续犯同类错，靠 1 次修正 + 轮数兜底 |
| 必填缺失 | 数组元素漏 `interviewer_id` | ③ 参数校验 | 同上，精确到 `recommend[0]` | 深层嵌套错误可读性下降 |
| 工具内部异常 | 文件缺失、KeyError | 执行兜底 | 包成 `{"error": ...}` 回灌 | 掩盖了真实 bug，需配合日志排查 |
| 工具返回空 | 无时段、无覆盖结论 | 无（W3 反思负责） | 由 W3 反思层提示"不要编造" | 两周期职责边界需保持清晰 |
| 模型自说自话 | 编造工号、编造时段 | ④ 输出校验 | 拦截编造工号；时段靠反思 | 时段无白名单可比对 |
| 越界承诺 | "已自动派单" | ④ 输出校验 | 阻断 + 回灌修正 | 语义等价改写拦不住 |
| 输出为空 | 模型只返回空 content | ④ 输出校验 | 判失败，回灌 1 次 | 再失败即终止 |
| 死循环 | 反复调工具不收敛 | ⑤ 轮数 | 结构化终止 | 无重复调用检测，只在预算内浪费 |

这张表也是后续迭代的路线图：残留风险最重的一格（语义越界）指向结构化输出改造，第二重（无重复检测）指向 fingerprint 去重。

# 七、可观测与度量

## 7.1 trace 结构

每步都记，不只记结果：

```json
{
  "question": "...",
  "steps": [
    {"step": 1,
     "tool_calls": [{"name": "notify_hr_override",
                     "args": {"candidate_ref": "demo-001"},
                     "status": "ok",
                     "output_keys": ["override_applied", "preferred_interviewer_ids", "..."]}]},
    {"step": 4, "tool_calls": [], "output_check": {"ok": true, "errors": [], "warnings": []}}
  ],
  "terminated_by": "answered"
}
```

记 `status`（`ok` / `invalid_args` / `unknown_tool`）而不只记成功调用，是因为**失败尝试才是优化 prompt 与 schema 的一手材料**。只看成功路径，永远不知道模型最爱在哪个字段上犯错。

## 7.2 四个可迭代指标

| 指标 | 计算口径 | 用来判断什么 |
|---|---|---|
| 收敛步数 | `answered` 时的 step | 工具链是否过长、是否该合并工具 |
| 参数拒绝率 | `invalid_args` 次数 / 工具调用总次数 | schema 描述是否含糊、prompt 是否需要补示例 |
| 修正成功率 | 回灌后下一轮通过的比例 | 错误信息是否足够可操作 |
| 终止原因分布 | 四值占比 | `max_steps` 高→预算或工具设计问题；`output_*` 高→输出约束不足 |

本期因样本只有一次真实运行，这些指标只有结构性意义，还不能做统计结论。要真用起来，需要跑几十条真实请求攒分布——这也是我把它写成"可算口径"而不是"已知结论"的原因。

# 八、真实运行验证

真实网关（`DRY_RUN=0`，`glm-5.3`），完整输出见 `docs/运行结果-W4.txt`。

**场景 1｜完整链路收敛**（`uv run w4-loop`）

```
输入校验通过（81 字符）
第 1 步 notify_hr_override(demo-001)         → HR 指定 XA-1042，manual_highest
第 2 步 query_interviewer_calendar(XA-1042)  → 3 个时段，read_only=true / locked=false
第 3 步 push_recommendation_card(...)        → 草稿，pushed=false / auto_dispatch=false
第 4 步 模型作答，输出校验通过，循环结束
结果：ok=True  terminated_by=answered
```

三点值得注意：模型**没有自己加戏**去调 `fetch_resume_from_hr_system`（任务不需要简历）；卡片参数里的 `recommend` 数组元素字段完整，未被参数闸门拒绝；回答里主动写了 `pushed: false`、`auto_dispatch: false`，说明系统提示里的边界约束被吃进去了。

**场景 2｜轮数兜底**（`--max-steps 2`）

```
第 1 步 notify_hr_override → 第 2 步 query_interviewer_calendar
[终止] 达到最大轮数 2，结构化终止（未产出最终回答）
结果：ok=False  terminated_by=max_steps（退出码 1）
```

关键点：终止时**没有返回半截答案**。如果第 2 步就把已有信息当结论交付，用户会拿到一份缺卡片的"推荐结果"，比报错更危险。

**场景 3｜参数闸门**（单元级，零 token）

| 用例 | 结果 |
|---|---|
| `channel='mail'` | 拒绝：取值不在 `['group','private']` 内 |
| 日历工具传 `channel` | 拒绝：未定义字段 |
| `recommend[0]` 缺 `interviewer_id` | 拒绝：元素缺必填 |
| `candidate_ref=1`、`recommend='x'` | 拒绝：两处类型错误 |
| 合法参数 | 放行 `errors=[]` |

**场景 4｜输出闸门**

| 用例 | 结果 |
|---|---|
| 空回答 | 拒绝：最终回答为空 |
| 含手机号 | 拒绝：PII 未脱敏 |
| 推荐 `XA-9999` | 拒绝：池中不存在，疑似编造 |
| 「已自动派单」 | 拒绝：业务越界表述 |
| 正常回答 | 通过，仅可能带 warning |

# 九、复杂度落点（对应评分）

课程说"看复杂程度评分"。我的判断是：**复杂度应该落在"出错之后还能正确收场"，而不是功能清单的长度**。本期五处落点：

1. **校验分层而非堆叠**：四层各管一件事，越靠边界越早拦，且都不 import 业务代码，可独立单测；
2. **校验可回灌**：把"拦截"升级成"纠错"，错误带字段路径、期望值、修正提示；
3. **终止可枚举**：四种原因 + 退出码，调用方无需解析文本；
4. **状态不漂移**：四条不变量（单步单次决策、调用必有应答、失败必有原因、出口只有四个）；
5. **复用不自造**：直接挂 W3 四个工具，换工具只改 schema，Loop 不动。

如果只让我保留一条，我会保留第 2 条——因为它把校验从"挡人的墙"变成"带路的标"，是 Agent 能自我修正的前提。

# 十、局限与下一步

诚实列清楚，避免把作业写成"全部完成"：

| 局限 | 影响 | 下一步 |
|---|---|---|
| 输出校验只认字面 | 语义等价的越界拦不住 | 改结构化输出：结论只在受控字段表达，文本仅用于渲染 |
| 无重复调用检测 | 模型可能空转烧预算 | 对 `(tool_name, args)` 做 fingerprint，重复即回灌提醒 |
| 无工具超时 | 接真实 API 后单次调用可能吃满预算 | 执行层加 `timeout`，超时按工具错误回灌 |
| schema 子集不含 `oneOf/$ref` | 复杂 schema 需手工拆 | 需要时改用 pydantic 从函数签名自动生成 |
| 未做断点续跑 | 长任务中断需重来 | W5 之后引入状态持久化 |
| 校验逻辑内嵌在 Loop | 新增校验要改主流程 | 抽成 middleware 链，按需注册 |

工程边界保持不变：工具仍是 W3 的四个本地只读/草稿实现，招聘系统 / 飞书 / 日历真实适配器未接（`tools.py` 内标 TODO）；`DRY_RUN` 分支只用于验证 Loop 结构，不作为作业真实记录；简历不入库、用完即删的业务红线在本周未做任何放宽。
